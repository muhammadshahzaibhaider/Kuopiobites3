# Admin view load/save audit (pre-change)

Audit date: 2026-10-17. This is a read-only audit of the deployed `frontend/` application and its `backend/` API before feature implementation. No behavior described as failing below was assumed without inspecting its path; the settings failure has **not** yet been reproduced.

## Authentication and navigation

- `/admin` is the deployed entry point (`frontend/src/app/admin/page.tsx`). Its session-storage flag only controls whether the login gate is rendered; the actual login uses `POST /api/auth/admin-login` and an HttpOnly staff cookie. Mutating admin routes separately enforce `requireStaff("manager")` or stronger, and CSRF middleware applies to writes. Preserve that separation; the client flag is not authorization.
- The routed admin leaves are Dashboard; Orders (live queue, history, refunds); Dining (calendar, reservations, slot settings); Menu (items, categories, toppings, today's special); Customers; Analytics (sales, item performance, peak hours); Admin (staff session/activity); Settings (general, restaurant info).
- There is no dedicated Off-menu page and no Promotions/Delivery-rules editor in the navigation. The item list has an “Availability: Sold out” filter, but users must navigate to Menu → Items and select it.

| Dashboard | `ShopProvider.refresh()` loads settings, categories/items/translations, then staff orders/reservations and (best-effort) customers. | Order status/refund APIs and settings writes. | Dashboard figures are computed from the client’s current `orders` array (API list is bounded); sales include orders regardless of payment status. Revenue and off-menu cards navigate to generic views rather than a focused report/filter. Settings switch calls are fire-and-forget and show a success toast before persistence is confirmed. |

Status changes have a generic error toast; the displayed status is not a durable ready-time/ETA. Refunds rely on the existing payment path and should not be broadened. |
| Dining — calendar/reservations | Staff refresh loads `GET /api/reservations`; settings are loaded through `/api/settings`. | Reservation status/delete APIs; blocked dates/slots and capacity are written through full `PUT /api/settings`. | Reservation operations are persisted. Blocked-slot/date textareas save on every edit and do not await/show the settings result, making network failures look like success and risking overlapping snapshot writes. |

Backend currently includes inactive toppings in `Settings.toppings` while also recording them in `offOptions.topping`; this leaves the customer picker/validator path ambiguous and needs correction. Per-item groups and independent modifiers are not configurable. |

Most fields call save on each keystroke and do not wait for the result; failed or overlapping writes are hard to diagnose. There is no Offers editor here. |
| Customers | `GET /api/customers` is attempted after a manager staff session; the endpoint is manager-protected. ## Settings persistence boundary observed

`backend/src/server.ts` validates the complete settings snapshot, then `backend/src/supabase-settings.ts::saveSettings` performs sequential writes to `shop_settings`, categories, menu items, toppings, promotions, and today's-special rows. These writes are **not transactional**. A later failure can leave earlier writes committed, while the API currently returns a generic internal error. This is a verified structural limitation, **not** a verified cause of the user-reported save error. Reproduction and failure-localization are still required before claiming a cause. The implementation must avoid concurrent whole-snapshot writes from individual keystrokes and must re-fetch after a confirmed save.

## Other implementation constraints found

- Customer text and Finnish/English dictionaries live in `frontend/src/lib/i18n.tsx`; `frontend/src/lib/strings.ts` does not exist.
- The server remains the pricing/availability authority in `backend/src/logic.ts`: exact variant labels (including `""` for one-price items), raw modifier option labels, pizza `sizeLabel === variantLabel`, builder flag validation, and topping validation against settings are existing contracts.
- `ItemModal` currently uses a vertically scrollable, height-limited panel. `PizzaSheet` already has a mobile bottom-sheet/sticky-footer pattern that can be reused.
- The base schema/migration is under root `supabase/migrations/`, which is outside the approved feature-edit boundary. Any additive feature migration must be placed/documented under `backend/` and remain idempotent and non-destructive.
- The repository has no live database credentials in this audit, so database-failure reproduction and direct Vercel/public-site checks are outstanding. Vercel status success alone does not prove `/api/health` or the public website response.
