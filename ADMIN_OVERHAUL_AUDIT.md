# Admin overhaul — pre-change root-cause audit

Repository inspection completed before implementation. The root `package.json` builds `src/`; `frontend/src/` is a parallel copy with a partial real-API integration, while the active root app still imports a local-storage API stub. The backend is an Express/Supabase service with staff role checks and several CRUD routes; the frontend does not currently use it.

1. **Admin/customization:** `src/app/admin/page.tsx` grants access with a hard-coded browser-side `admin / kuopio2026` check. `src/lib/api.ts` labels its methods as stubs and writes to `localStorage`; `ShopProvider` derives menu edits, settings, orders and categories from local storage or bundled constants. Therefore the admin UI never calls the existing authenticated backend or writes catalog/settings data to the database. Several controls also update state optimistically and do not wait for a save result.
2. **Delivery offers:** the active order repricer supports only one global `deliveryFee`/`radiusKm`; delivery validation only checks for a `70xxx` postcode. There is no rule table/model, item weight, geocoder, or rule evaluator, so distance/weight promotions cannot be authored or safely priced.
3. **Off-menu view:** the dashboard’s card navigates to the generic Items page, whose availability filter starts at `all`. There is no dedicated off-menu view or search/category-filtered unavailable-only list. It is currently local-only, so toggling does not reliably change the public catalog.
4. **Revenue/settings:** the chart is a small in-house CSS bar renderer (no missing chart package), but it aggregates the browser’s demo `kb_orders` cache, which is empty on a fresh session and is not the backend orders table. Settings writes in the active root app only serialize to local storage; the backend settings route exists, but no root caller reaches it. The reported save error is therefore a frontend/API wiring defect in the active app, not evidence of a missing chart library.
5. **Ready timer:** order acceptance only changes status. There is no `ready_at`/note column or API payload, and root order status can be simulated from order age. Neither the admin queue nor the public tracker can show a persistent estimate.
6. **Delete/archive:** the root editor offers deletion only for locally-created custom items. Existing catalog rows have no delete action; the backend’s item delete is physical (though order line snapshots and `ON DELETE SET NULL` preserve order history), categories can fail on an item FK, and topping configuration has no first-class CRUD endpoint.
7. **Biryani:** product entries are hard-coded in `src/lib/menu.ts` and have no admin-managed portion/variant editor. Their separate item IDs prevent a single selector experience; no data migration currently consolidates them.
8. **Samosas:** packs are hard-coded as separate products; no reusable quantity/pack-variant editor exists. Replacing them without a versioned variant migration would risk losing IDs/prices used by old orders.
9. **Custom product system:** the database already has `price_variants`, `mods` JSON and an `item_toppings` join, but the active root admin only edits local text/price overlays and a global toppings list. There is no end-to-end persisted editor for variants, option rules, weight, topping visibility or item-topping relationships, and public cards still source their base products from static `MENU`.
10. **Item modal:** the dialog is constrained to `max-h-[86vh]` with `overflow-y-auto`; its full content is inside that scroller and the action row is not sticky. On narrow screens, the header/action flex children can also exceed the viewport. This creates the visible scrollbars and awkward layout rather than a charting or browser issue.

**Safe implementation direction:** make the root app use the existing same-origin API client pattern and staff cookie/CSRF flow; extend the current Supabase schema with additive migrations and server-validated routes; preserve bundled menu data as a first-paint fallback only. Never use client-side values as price authority and keep historic order lines denormalized.
